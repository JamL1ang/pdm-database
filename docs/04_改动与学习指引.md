## 3. 怎么自己验证（建议按顺序做一遍）

1. **跑脚本**：MySQL 8 里整体执行 `schema.sql`（脚本开头会 DROP 旧表，可重复运行）。
2. **跑校验**：`python tests/validate_seed_data.py`，零报错说明示例数据的外键/批次关系自洽。这个脚本不连数据库，直接解析 SQL 里的 INSERT，适合在没有 MySQL 的机器上先自查。
3. **看查询 1**：应返回 X100 的 5 行文档，分属 `v1.0`（2 行）和 `v1.1`（3 行）—— 验证「版本 → 多份文档」。
4. **看查询 2-B**：外壳、显示屏、电池各 2 家，接头、PCB板、芯片各 2 家，处理器 1 家 —— 验证题目 7 两个方向。
5. **对比 2-A 和 2-C**：2-A 是「最多能供几种」，2-C 是「某批次实际供了几种」，数字应该明显不同 —— 这是答辩时最容易被问到的一点。
6. **换序列号**：把 3-③ 的 `'SN0001'` 改成 `'SN0003'` 再跑。同一个型号 X100，外壳/显示屏/接头/芯片的供应商会变，因为两台机器分属批次 1 和批次 2。这就是缺陷定位的逻辑。
7. **验证约束**：把末尾三条注释掉的 INSERT 解开执行，应分别报主键重复、复合外键失败、CHECK 失败；截图可放进报告。

## 5. 答辩时可能被问到的三个问题

1. **「同一批产品供货源相同」怎么保证？**
   → `batch_*_source` 用 `PRIMARY KEY(batch_id, 物料id)`，同批次同物料只能有一条记录；单品通过 `batch_id` 继承，不需要逐台存。
2. **「可供清单」和「批次供货源」有什么区别？**
   → 前者是能力（一家可供多种、一种可有多家），后者是事实（某批次实际选了一家）。少了后者就无法追溯缺陷。
3. **为什么部件和材料要分两张表？**
   → 语义不同、属性不同（部件有采购/自产标志、参与产品 BOM；材料只参与自产件构成）。代价是中间表变多。若重设计，可合并成统一物料表简化统计 —— 承认取舍比硬说「只能这样」更加分。
