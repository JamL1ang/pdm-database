# C1 产品数据管理（PDM）数字化系统 — 需求分析与设计说明

> 对应 `schema.sql` v2。数据库：MySQL 8.x，库名 `pdm_db`，字符集 `utf8mb4`。

## 1. 题目条目 → 数据库模式映射

| 题号 | 业务描述 | 落到的表 / 约束 |
| --- | --- | --- |
| 1 | 多类产品，同类有系列、型号规格、价格 | `product_type`、`product`（`series` / `model` / `price`） |
| 2 | 保存迭代版本的设计说明书、设计图等文档 | `product_version`（迭代版本）+ `document`（挂版本），`UNIQUE(product_id, version_no)` |
| 3 | 产品由多个部件构成 | `product_component`（M:N 中间表，带 `quantity`） |
| 4 | 同一部件可用于不同产品 | 同上；示例数据里外壳、处理器等同时出现在 3 个产品的 BOM 中 |
| 5 | 部件来源：采购件 / 采购材料自产 | `component.source_type` + `CHECK (source_type IN ('采购','自产'))` |
| 6 | 自产部件由多种材料组成 | `component_material`（M:N 中间表，带 `quantity`） |
| 7 | 部件/材料 ↔ 供应商 多对多 | `component_supplier`、`material_supplier`（均带 `supply_price`） |
| 8 | 同一批产品供货源相同；每个产品唯一出厂序列号 | `batch`、`product_instance`（`serial_no` 主键）、`batch_component_source` / `batch_material_source`（`PRIMARY KEY(batch_id, 物料id)` 保证批次内唯一供应商） |
| 9 | 三类查询 | 见 `schema.sql` 末尾「三、查询」：查询 1、查询 2（2-A/2-B/2-C）、查询 3（3-①/②/③） |

题目总述提到的「配置、CAD 文件、权限信息」：CAD 文件以 `document.doc_type = 'CAD文件'` 纳入文档体系；权限以 `sys_role` / `sys_user` / `doc_permission` 做简化实现；产品配置（选配变体）属于进一步扩展，本简化模式未展开，见第 7 节。

## 2. 表清单（18 张，分 5 组）

| 组 | 表 |
| --- | --- |
| 产品与文档 | `product_type`、`product`、`product_version`、`document` |
| 部件与 BOM | `component`、`material`、`product_component`、`component_material` |
| 供应商 | `supplier`、`component_supplier`、`material_supplier` |
| 批次与追溯 | `batch`、`product_instance`、`batch_component_source`、`batch_material_source` |
| 权限（扩展） | `sys_role`、`sys_user`、`doc_permission` |

## 3. 关键设计决策

### 3.1 为什么把「产品版本」提成独立实体

题目第 2 条说的是**产品的迭代版本**，不是文档自己的版本号。这两者容易混：

- 产品版本 `v1.1` 是一次设计改版，底下可以同时挂设计说明书、设计图、CAD 文件；
- 文档修订号 `R1` 只是这份文件自己的第几次修改。

v1 把 `document` 直接挂在 `product` 上、只留一个 `version` 字段，结果「同一次改版下的多份文档」无法归组，也没法记录改版说明和发布日期。v2 提成 `product → product_version → document` 三层，`UNIQUE(product_id, version_no)` 防止同型号版本号重复。

### 3.2 为什么必须有「批次供货源」两张表（本题核心）

第 7 条要求的是**「谁能供什么」**，第 9 条要求的是**「这台机器实际用了谁家的」**，这是两件不同的事：

- `component_supplier` / `material_supplier`：可供清单，是长期的、能力层面的关系；一种物料可以对应多家。
- `batch_component_source` / `batch_material_source`：某一批次的实际用料来源，是事实记录；**批次 + 物料只能对应一家**。

只有前者，缺陷溯源根本查不出来（只能列出「可能的供应商」）。题目第 8 条「同一批产品用的部件和材料供货源相同」正好给出了建模依据：把供应商绑定在**批次**上，而不是每台机器上。于是同一批次的所有 `product_instance` 天然共享同一份供货记录，既避免逐台重复存数据，又满足约束。

两张表都用**复合外键**指回可供清单，例如：

```sql
FOREIGN KEY (component_id, supplier_id)
    REFERENCES component_supplier(component_id, supplier_id)
```

这保证不能给某批次指定一个「从没登记过可供关系」的供应商，是本题里最有价值的一处约束。

### 3.3 部件与材料为什么分成两张表

题目里二者语义确实不同：部件参与产品 BOM，材料只参与自产部件的构成；部件还有「采购/自产」属性，材料没有。分开建表读起来更直观，代价是供应商关系要两张中间表、批次供货也要两张，统计查询得 UNION 一次。

另一种做法是合并成一张统一物料表（`item` + `item_type` 字段），供应商和批次各只需一张中间表，统计更简单。两种都正确，属于设计取舍。本作业沿用 v1 的分表结构，避免改动过大；若重新设计，推荐统一物料表。

### 3.4 序列号为什么挂在 `product_instance` 而不是 `product`

`product` 是**型号**（设计对象，如 X100），一个型号会生产成千上万台；`product_instance` 是**单台出厂设备**。`serial_no` 作为主键放在实例表，再通过 `batch_id` 继承整批供货源，形成：

```
serial_no → batch_id → batch_*_source → supplier_id
```

这是查询 3 的完整链路，也是「探究产品缺陷产生原因」的数据基础。

### 3.5 权限信息的简化处理

按「角色 + 文档类型」控制读写，不细化到单份文档、不建菜单/操作权限表。三张表与主流程解耦，删掉也不影响题目 1–9 条。

## 4. 完整性约束清单

| 类型 | 具体约束 | 作用 |
| --- | --- | --- |
| 实体完整性 | 所有表均有主键；中间表用联合主键 | 防止重复 BOM 行、重复供货关系 |
| 参照完整性 | 全部外键；两张批次供货表的复合外键 | 只能引用已登记的可供关系 |
| 用户定义完整性 | `CHECK(source_type IN ('采购','自产'))` | 部件来源合法 |
| 唯一约束 | `product_version(product_id, version_no)`、`document(version_id, doc_type, doc_rev)`、`batch.batch_no`、`component_code`、`material_code`、`serial_no` | 业务键不重复 |
| 业务规则 | `batch_*_source` 的 `PRIMARY KEY(batch_id, 物料id)` | 同一批次每种物料只有一个供货源（题目 8） |

`schema.sql` 末尾附了 3 条故意违规的 INSERT，注释形式保留，可解开执行并截图证明约束生效。

## 5. 规范化说明

- 所有表属性均为原子值，无重复组、无多值属性 → 满足 1NF。
- 非主属性完全依赖整个主键：中间表的 `quantity` / `supply_price` 依赖联合主键，不依赖其中一部分 → 满足 2NF。
- 非主属性之间无传递依赖：供应商名称只存在 `supplier`，产品信息只存在 `product`，批次供货表只存 ID → 满足 3NF。
- 唯一的刻意冗余：`product_instance` 同时存 `product_id` 和 `batch_id`，而 `batch` 里也有 `product_id`。这是为了查询方便，严格来说可由 `batch_id` 推出；简化模式未加触发器保证两者一致，属于已知简化点。

## 6. 三类查询的实现思路

| 查询 | 链路 | 统计方式 |
| --- | --- | --- |
| 查询 1 设计文档 | `product → product_version → document` | 按版本发布日期、文档类型排序 |
| 查询 2-A | `supplier` + 两张可供清单各先聚合再 LEFT JOIN | 按供应商统计可供物料种类数 |
| 查询 2-B | `component/material` JOIN 可供清单，UNION ALL | 按物料统计可选供应商数 |
| 查询 2-C | 两张批次供货表 UNION ALL → `batch` → `supplier` | 按批次统计各供应商实际供货物料项数 |
| 查询 3 | `product_instance → batch → batch_*_source → supplier`，沿两层 BOM 展开 | 3-① 部件层、3-② 材料层、3-③ UNION ALL 合并 |

**2-A 的一个易错点**：v1 把 `component_supplier` 和 `material_supplier` 同时 `LEFT JOIN` 到 `supplier`，当某供应商既供部件又供材料时行数会相乘。`COUNT(DISTINCT ...)` 能侥幸得到正确计数，但只要再加 `SUM(supply_price)` 就会算错。v2 改成两个子查询各自 `GROUP BY` 后再连接，从根上消除笛卡尔积。

**2-A 与 2-C 的区别**要能说出来：前者是「能供什么」（能力），后者是「这一批真的用了谁家的」（事实）。

## 7. 已知简化与可扩展点

- 产品配置 / 选配变体未建模（可加 `configuration` + `configuration_item`）。
- BOM 只展开两层（产品→部件→材料），未做递归多层 BOM；MySQL 8 可用递归 CTE 扩展。
- 权限只到「角色 + 文档类型」粒度。
- 采购订单、库存、价格有效期、文档二进制内容均未纳入，文档以 `file_path` 指向外部文件。
- `product_instance` 与 `batch` 的 `product_id` 一致性未用触发器强制。
